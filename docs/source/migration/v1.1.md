# Migrating to DataEval v1.1

DataEval Flow now builds on DataEval v1.1. Most of what changed upstream is invisible from here — a pipeline is
described in configuration, not in DataEval calls, so the API renames and deprecations in
[DataEval's own migration guide](https://dataeval.readthedocs.io/en/latest/migration/v1.1.html) do not reach your
`params.yaml`.

What *does* reach you is the numbers. Several statistics are reported on a different scale, and `Balance` is
corrected for chance. Nothing about your dataset changed, but results computed before the upgrade are not comparable
against results computed after it.

## At a glance

| You will notice | Because | Do this |
| --- | --- | --- |
| Pixel statistics are orders of magnitude larger | They are reported in stored units, not normalized to `[0, 1]` | Nothing — but do not compare against stored values |
| A stale cache is ignored and everything recomputes | The cache version moved to `v3` | `rm -rf <cache_dir>/v2` to reclaim the space |
| `Balance` rankings changed between factors | Values are corrected for chance | Recompute any stored baseline before comparing |
| Class-balance counts changed | A counting bug in `ClassBalance` was fixed | Nothing — the new counts are the correct ones |
| Visual statistics on float imagery read `NaN` | Float data no longer gets an inferred range | Set `value_range` — see [below](#new-configuration) |
| Outlier flag rates look the same | They are — no flag moved | Nothing |

## Clear the cache

The workflow cache is versioned, and v1.1 bumped it to `v3` because the pixel rescale changes stored statistics.
Old versions are ignored rather than deleted, so nothing breaks — but nothing is reclaimed either:

```bash
rm -rf <cache_dir>/v2        # drop the superseded version
```

The next run recomputes. See {doc}`../how_to/reuse_results_with_cache` for what the cache holds and what invalidates
it.

## Stored results need recomputing

This is the change that matters for test and evaluation, because it breaks comparison against a baseline rather
than breaking a run.

**Pixel statistics are reported in the units the data is stored in.** `normalize_pixel_values` now defaults to
`False`. A 12-bit image whose mean read `0.4944` now reads `2024.59` — the same measurement, a different scale.

**`Balance` is corrected for chance.** Mutual information between two factors carries a component attributable to
cardinality alone, and v1.1 subtracts it. Factors of differing cardinality therefore rank differently against each
other than they did.

**`ClassBalance` counting was fixed.** Where a view used it, the resulting membership can differ.

An envelope archived before the upgrade is still a valid record of what that run computed. It is not a valid
comparison against a fresh run. Recompute the baseline before drawing a conclusion from a difference — see
[Provenance](../concepts/Provenance.md) for why the envelope records the tool version that produced it.

## Your outlier thresholds still hold

A rescale of this size invites the question, so to state it plainly: **no outlier flag moves.**

Every threshold method DataEval Flow offers — `adaptive`, `modzscore`, `zscore`, `iqr` — is location-scale
equivariant. Each measures distance in units of the distribution's own spread, so multiplying every value by a
constant moves the statistic and the threshold together. A tuned `outlier_threshold` is as correct after the upgrade
as before it, and flag *rates* are unchanged.

The one exception is a fixed cutoff compared against a raw statistic rather than against the distribution. DataEval
Flow has no configuration that does this, so it does not arise here.

Visual statistics did not move either, for a different reason: they now read the 0–255 display range regardless of
encoding, so one image answers the same whatever it is stored as.

## New configuration

Four settings arrived with this release. All are optional.

Three govern how metadata factors are discretized before bias, balance, diversity, and coverage analyses read them,
and are accepted by `data-analysis`, `data-cleaning`, `data-coverage`, and `ood-detection`:

```yaml
workflows:
  - name: coverage_check
    type: data-coverage
    metadata_auto_bin_method: uniform_width      # or uniform_count / clusters
    metadata_exclude: [id, filename]
    metadata_continuous_factor_bins:
      elevation: 8
```

The fourth declares the interval float image data occupies. Integer encodings state their own; float data does not,
and v1.1 answers `NaN` rather than inferring one:

```yaml
    value_range: [-50.0, 50.0]
```

Affected without it: the whole `visual` group, pixel histogram and entropy, and dimension depth. Leave it unset for
ordinary integer imagery — the `[0, 1]` and `0–255` float conventions are still detected automatically.

{doc}`../how_to/configure_metadata_binning` covers all four in full, including how to read back what a run decided.

## Results now record how factors were treated

Because binning changes what evaluators read, every result now carries the decisions. `metadata.metadata_binning`
records each factor's type, its level, whether it was binned or digitized, and the observed range and population of
every bin. `metadata.diagnostics` carries the warnings the run raised — ranges that could not be resolved, bin
requests that were ignored. Both appear in the text report under **METADATA FACTORS**.

Nothing is required of you here; it is new information in an existing envelope.

## Factor naming

Image statistic factors are named for the level they belong to: `brightness` became `unit_brightness`, and the
`target_*` family became `instance_*`. Metadata factors are also binned at their own level now, rather than over the
detection rows, so a per-image factor is described by one value per image instead of one per detection.

:::{warning}
This rename applies to **DataEval's image statistic factors**, not to DataEval Flow's configuration keys. In
particular, `target_outliers` under `health_thresholds` is a DataEval Flow key and is **unchanged**:

```yaml
    health_thresholds:
      target_outliers: 10.0        # still correct — do not rename
```

See {doc}`../how_to/configure_outlier_detection`.
:::

One further vocabulary note, since the word `level` now means two things in results. Per-factor metadata summaries
report a {term}`metadata level <Metadata Level>` — `sequence`, `unit`, `track`, or `instance`. Duplicate groups
report `item` or `target`, which is a different axis and did not change. Classwise outlier pivots previously
reported `level` too; that key is now `count_basis`, with values `image` and `annotation`, so the three cannot be
confused.

## New capability

View operations are a pass-through to `dataeval.data`, so v1.1's additions are usable immediately: `Crop`,
`Resize`, `SelectChannels`, and `TorchvisionTransform`. See {doc}`../how_to/build_dataset_views`.

Beyond that, v1.1 adds ontology support, multi-object tracking, `Representation` and `Coverage`, and
`DriftWasserstein`. Where DataEval Flow exposes these it is documented in the relevant guide; the rest are reachable
only through DataEval directly.

## What you do not have to do

DataEval v1.1 deprecates a number of APIs — `per_channel=True`, `Select` and `dataeval.selection`,
`Metadata.image_data` / `target_data` / `raw_data`, `ClassifierUncertaintyExtractor`, `Balance.num_neighbors` — and
removes `DuplicatesOutput["dataset_index"]` in favor of `["dataset_indices"]`.

**None of these are reachable through a DataEval Flow configuration.** They matter only if you also call DataEval
directly alongside your pipeline, in which case
[DataEval's migration guide](https://dataeval.readthedocs.io/en/latest/migration/v1.1.html) is the reference.

The one vocabulary change with a DataEval Flow counterpart is `selections` / `selection` / `steps`, which became
`views` / `view` / `operations`. That is a DataEval Flow rename, it predates this release, and the old keys are
still accepted with a deprecation warning — see
{doc}`../how_to/build_dataset_views`.

## Checklist

1. `rm -rf <cache_dir>/v2`.
2. Recompute any stored image statistics or `Balance` results you compare against.
3. Set `value_range` if your imagery is float-valued.
4. Leave `outlier_threshold` and `target_outliers` alone.
5. Re-read a result's **METADATA FACTORS** block to confirm factors were binned the way you expect.

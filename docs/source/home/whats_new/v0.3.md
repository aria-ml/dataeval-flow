# What's New in v0.3

v0.3 is built around one question: **is this dataset ready to train on?** A new `audit` preset answers it with a
verdict a training job can gate on. Every workflow type is now a **preset**, a chain of evaluators, checks and
transforms you can read, copy and change, and you can write chains of your own. Results come with an **HTML report**
and **content digests** that show which data was judged, and `dataeval-flow serve` runs pipelines over HTTP as a
**preview**. Flow now requires **DataEval 1.2** and Python 3.11 or newer.

v0.3 breaks more than v0.2 did. Workflow types are renamed, `data-analysis` and `parameter-sweep` are gone, every
workflow returns a `ChainResult`, and health thresholds move under `checks:`. A v0.2 config fails to load, naming each
key and type v0.3 no longer takes. This page covers each move, and the {doc}`Change Log <../changelog>` lists every
old key and where it went.

For the v0.2.2 to v0.2.5 patches, see the {doc}`Change Log <../changelog>`.

---

## At a Glance

| Feature / Change | Impact | Action Required |
| --- | --- | --- |
| **Presets** | Every workflow type is a chain of steps, and most are renamed | Rename `type:`; move thresholds under `checks:` |
| **Audit verdict** | One chain over train and its evaluation splits says whether to train | Replace `data-analysis` with `audit` |
| **Custom workflows** | Chain evaluators, checks, transforms and presets yourself | None |
| **Task matrices** | Run any task over a grid of settings | Replace `parameter-sweep` with `matrix:` |
| **HTML report** | `result.html`, with thumbnails of the items a finding names | None |
| **Provenance** | Digests and manifests of the data a run read, and `dataeval-flow verify` | None |
| **Service (preview)** | `dataeval-flow serve` queues pipelines over HTTP | None |
| **DataEval 1.2** | Missing metadata stays null; Outliers needs 20 items; Coverage's criteria are DataEval's | Recompute baselines |
| **Python API** | Results are `ChainResult`s; internal modules are private; imports move | Update imports and result readers |
| **Platform** | Python 3.11+; Poetry dropped; health warnings exit `3` | Update CI |

## 1. Workflow Types Are Presets

A preset is a workflow type whose settings expand into a chain of steps: evaluators that measure, checks that judge
what they measured, and transforms that make new datasets. A preset runs like any chain, and you can run it as one
step of a workflow of your own. The {doc}`Preset Catalog <../../reference/presets>` shows each preset's chain, and
`dataeval-flow steps` lists every step type with its ports and settings.

Presets are named for the question they answer:

| v0.2 type | v0.3 type |
| --- | --- |
| `data-cleaning` | `quality` |
| `data-analysis` | `audit` (see [section 2](#2-judge-readiness-with-audit)) |
| `data-coverage` | `scope` |
| `data-splitting` | `splits` |
| `data-prioritization` | `prioritization` |
| `drift-monitoring`, `ood-detection` | `shift`, one preset taking drift and OOD detectors in one `detectors:` list |
| `parameter-sweep` | a `matrix:` on the task (see [section 3](#3-compose-your-own-chains)) |

Three presets are new: `bias` (class balance and how metadata factors relate to the class), `taxonomy` (labels judged
against a declared ontology) and `triage` (metadata a dataset failed to read, and the policy that repairs it).

### How to upgrade

Each preset holds a step's settings in a block named for the step, and each check's bounds under `checks:`, keyed by
check type:

```yaml
# v0.2
workflows:
  - name: clean
    type: data-cleaning
    outlier_method: zscore
    outlier_flags: [pixel]
    health_thresholds:
      image_outliers: 5.0

# v0.3
workflows:
  - name: clean
    type: quality
    outliers: {flags: [pixel], outlier_threshold: zscore}
    checks:
      image-outliers: {warning: 5.0}
```

- A check warns only past its bound, not on reaching it.
- `value_range` moves to the dataset entry, and the `metadata_*` binning fields to a named `metadata:` policy.
- Presets use DataEval's default for every setting, except that `prioritization` ranks `hard_first`, and `split` and
  `kfold` hold out 20% for test (and `split` 10% for validation), stratified.
- Findings are retitled for what they judge: Duplicates is Image Duplicates, Label Distribution is Class Imbalance,
  Embedding Coverage is Class Coverage. Update anything that matches on a title.
- Every preset returns a `ChainResult`. Each step's output is under `result.steps`, as in
  `result.steps["outliers"].output`, and the checks' judgments are its findings. The per-type result classes, such as
  `DataCleaningResult`, are gone.

`shift`'s drift and OOD detectors are evaluator entries now (`method: mmd` becomes `type: drift-mmd`). The
{doc}`Change Log <../changelog>` gives every old key of every preset and where it went.

## 2. Judge Readiness with `audit`

`audit` runs one chain over train and each evaluation split, and gives a verdict: Not ready, Ready with caveats, or
Ready. Its report lists the findings under five questions, the next step for each warning, and a record of each split's
items, classes, factors and digests.

### How to use

1. Name the splits in order, train first:

   ```yaml
   workflows:
     - name: release-audit
       type: audit
       outliers: {flags: [dimension, pixel, visual], outlier_threshold: adaptive}
       accepted:
         class-imbalance: "Rare class by design; weighted loss in training."

   tasks:
     - {name: audit-splits, workflow: release-audit, sources: [train, validation, test], extractor: bovw_ext}
   ```

   `blocking:` names the check types whose warnings block training, and `accepted:` records why a warning is accepted.

2. Gate on the verdict. `--require` (or `result: require:`, or `DATAEVAL_REQUIRE`) names the worst verdict that
   passes, and the command exits `4` when a task's verdict is worse:

   ```bash
   dataeval-flow --config pipeline.yaml --output ./output --require ready-with-accepted-risks
   ```

`audit` also runs as a step of a custom workflow, after a step that made the splits. See
{doc}`Gate training on an audit <../../how_to/gate_training_on_an_audit>` and
{doc}`the audit tutorial <../../notebooks/audit>`.

## 3. Compose Your Own Chains

A `workflows:` entry with `inputs:` and `steps:` chains evaluators, checks, transforms and presets. Each step reads an
input or an earlier step's output by address, such as `cleaning.clean`:

```yaml
workflows:
  - name: cleaning
    type: quality
    outliers: {flags: [pixel], outlier_threshold: adaptive}

  - name: tidy
    inputs: [data]
    steps:
      - {name: cleaning, workflow: cleaning, input: data}
      - {name: dataset, transform: export, input: cleaning.clean, format: coco}

tasks:
  - {name: clean_export, workflow: tidy, sources: [train]}
```

- **Transforms**: `view`, `merge`, `split`, `kfold`, `wrap`, `select`, `collect`, `remove` (DataEval's removal plans),
  `conform` (relabel onto an ontology) and `export` (COCO, YOLO, Hugging Face or VisDrone). An `export` step after
  `quality` replaces `mode: preparatory`.
- **One evaluator**: a top-level `evaluators:` entry runs one evaluator, and a task names it with `evaluator:` instead of
  `workflow:`.
- **Matrices**: `matrix:` on a task runs its entry once per combination of the values it lists, and its report opens
  with a table comparing the runs. It replaces `parameter-sweep`.
- **Plugins**: workflows, evaluators, transforms, extractors and image transforms register through entry points.

See {doc}`Chain steps into a workflow of your own <../../how_to/write_a_custom_workflow>`,
{doc}`Sweep settings with a matrix <../../how_to/run_a_matrix>`,
{doc}`Run a single evaluator <../../how_to/run_a_single_evaluator>` and
{doc}`Workflows as chains of steps <../../concepts/WorkflowsAsChains>`.

## 4. Reports

- **HTML**: `--output` writes `result.html`, a self-contained page with a card per finding, sortable tables and
  thumbnails of the items each finding names. `--no-report-images` turns the thumbnails off.
- **The `result:` block**: names the result files and picks their formats (`json`, `text`, `html`, `junit`,
  `markdown`), their detail, the exit-code gate (`fail_on:`) and limits on images and rows.
- **Exit codes**: a run that fails only on health warnings exits `3` (was `1`), so CI can tell it from a crash.
- **Text**: the text report is 80 columns wide by default (was 90).

See {doc}`View HTML reports <../../notebooks/view_html_reports>` and
{doc}`Read evaluation outputs <../../how_to/read_evaluation_outputs>`.

## 5. Provenance

- `dataset_digest()` gives SHA-256 digests of a dataset's content and metadata that don't depend on item order, and the
  `content-digest` evaluator records them in a run.
- A `content-digest` run writes a manifest of per-item hashes under `results/manifests/`, and
  `dataeval-flow verify` names the items a source has changed, lost or gained since:

  ```bash
  dataeval-flow verify output/results/manifests/audit-splits/content-digest-train.json --config pipeline.yaml --source train
  ```

- `provenance:` on a dataset entry records facts Flow can't measure, such as owner, licence and collection date.
- Every result records `library_versions` and the `device` its task ran on, and exports record a digest of what they
  wrote.

See {doc}`Provenance <../../concepts/Provenance>` and {doc}`Reproducibility <../../concepts/Reproducibility>`.

## 6. New Steps, Some Experimental

v0.3 adds steps across the catalog, among them `profile`, `divergence`, `completeness`, `factor-leakage` and the five
drift and two OOD evaluators, and the `leakage`, `class-sufficiency`, `untrained-classes` and `eval-coverage` checks.
The {doc}`Evaluator Catalog <../../reference/evaluators>` and {doc}`Check Catalog <../../reference/checks>` group
every step by the question it answers.

Some steps wrap DataEval features that are themselves experimental:

- `sufficiency` and `performance-sufficiency`: how much training data a model needs. See
  {doc}`the sufficiency tutorial <../../notebooks/measure_data_sufficiency>`.
- `feasibility` and `performance-feasibility`: whether a performance target is reachable. See
  {doc}`the feasibility tutorial <../../notebooks/check_target_feasibility>`.
- `parity` and `factor-parity`: metadata factors tied to the class.

An experimental step may change or be removed in any release without a deprecation cycle. Each experimental step type
warns with `dataeval_flow.ExperimentalWarning` the first time a run in the process uses it. The warning subclasses
DataEval's, so one filter silences both:

```python
import warnings

from dataeval_flow import ExperimentalWarning

warnings.filterwarnings("ignore", category=ExperimentalWarning)
```

## 7. `dataeval-flow serve` (Preview)

`dataeval-flow serve` is a long-running HTTP service that queues pipelines and runs each one as the batch command
would, keeping its logs and result files. It is a preview: its API may change or be removed in any release without a
deprecation cycle.

```bash
pip install "dataeval-flow[service]"
dataeval-flow serve --data /path/to/data --output /path/to/service-output
```

Every image includes it. See {doc}`Run Flow as a service <../../how_to/run_flow_as_a_service>` and the
{doc}`Service Reference <../../reference/service>`.

## 8. DataEval 1.2

Flow requires DataEval 1.2. Some of its changes reach Flow's results:

- **Metadata**: missing values stay null, and a factor mixing booleans with numbers or text is dropped as
  `mixed_types`.
- **Outliers**: DataEval fits a statistical threshold only to a population of at least 20. Below that,
  `image-outliers`, `target-outliers` and `class-outliers` are not assessed, with DataEval's reason.
- **Coverage**: `class-coverage` flags the classes DataEval's Coverage flags. Its cutoffs are DataEval's
  `dispersion_factor`, `isotropy_factor` and `near_duplicate_threshold`, set on the `coverage` evaluator or `scope`'s
  and `audit`'s `coverage:` block. The check's own `dispersion`, `isotropy` and `near_duplicates` are gone, and a
  near-duplicate fraction from an earlier run is not comparable.
- **Drift**: `drift-wasserstein` decides on the mean ratio over the dimensions, and its report says "Mean ratio".

See [DataEval's v1.2 migration guide](https://dataeval.readthedocs.io/en/latest/migration/v1.2.html).

## 9. Python API

- `run(config, data)` runs one workflow or evaluator on in-memory datasets. `run_tasks` returns results keyed by task
  name, and `on_result=` is called as each task finishes.
- `result.output` replaces `result.data`, and `result.type` replaces `result.name`.
- Internal modules (`cache`, `stats`, `policy`, …) are private. Config types import from `dataeval_flow.config`,
  `load_config` and `run_task` from `dataeval_flow`, and `Finding` from `dataeval_flow.steps`.
- Gone: the typed task configs (use `TaskConfig`), `select_tasks`, `load_config_folder` (`load_config` reads a folder),
  and the per-type output and report models.

## Upgrade Checklist

1. **Python 3.11**: install on Python 3.11 or newer, with uv, pip or conda; Poetry is no longer supported.
2. **Rename workflow types**: see the table in [section 1](#1-workflow-types-are-presets).
3. **Replace removed types**: `data-analysis` with `audit`, and `parameter-sweep` with a task `matrix:`.
4. **Move settings**: thresholds under `checks:`, step settings into their blocks (`outliers:`, `duplicates:`,
   `coverage:`, …), `value_range` onto the dataset, and binning into a `metadata:` policy.
5. **Update title matches**: anything matching on a finding's title, such as a dashboard or a CI script.
6. **Update result readers**: read a `ChainResult`'s `steps` and findings, and `result.output`.
7. **Update imports**: config types from `dataeval_flow.config`.
8. **Update CI**: exit `3` means health warnings, and `--require` gates on an audit's verdict.
9. **Recompute baselines**: DataEval 1.2 changes metadata, outlier and coverage results, and metadata cache entries
   recompute on upgrade.
10. **Pin experimental steps knowingly**: `sufficiency`, `feasibility` and `parity` may change in any release.

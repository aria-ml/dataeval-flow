# What's New in v0.2

v0.2 upgrades the underlying library to DataEval v1.1, introduces a data coverage workflow, and adds committed metadata
encoding policies. It is the first release with breaking changes: stored statistics change units, several
configuration keys are renamed, and the workflow cache is invalidated.

Five patches followed it, v0.2.1 to v0.2.5. Each has a section under Patch releases at the end of this page.

---

## At a glance

| Feature / change | Impact | Action required |
| --- | --- | --- |
| DataEval v1.1 upgrade | Stored pixel units, chance-corrected `Balance`, and shared split encodings | Recompute baselines before comparing. |
| New data coverage workflow | Pre-training gap analysis for classes & embeddings | Configure a `data-coverage` workflow. |
| Metadata encoding policies | Declared, reviewable, and pinned factor encodings | Define a `metadata:` policy block. |
| Float value range | Float imagery requires an explicit range to avoid `NaN` | Set `value_range` in your config. |
| Workflow cache v1 | v0.1 cache entries are not reusable and everything recomputes | Run `rm -rf <cache_dir>/v0`. |
| Renamed config keys | `selections`, `steps`, `selection` renamed | Rename to `views`, `operations`, `view`. |
| CUDA variants renamed (v0.2.1) | `cu118` / `cu128` image tags and the `onnx-gpu` extra are gone | Pull `cu126` / `cu130`, and install `onnx-cu126` or `onnx-cu130`. |
| YOLO split selection (v0.2.1) | Per-split loading restored | Add `split:` to YOLO dataset configs. |
| Headless CLI additions (v0.2.2) | `--task`, `--fail-on-warning`, `--version`, a `workflows` command, and a `health` block in results | None. |
| Environment variables and log format (v0.2.3) | `DATAEVAL_*` variables set the CLI parameters, and console logs gain timestamps | Pass `--log-format plain` where a tool reads bare messages. |
| Image repository and tags (v0.2.4) | Images publish to `aria/dataeval-flow`, and the floating tags are gone | Pull `latest-<variant>`, or pin `<version>-<variant>`, from the new repository. |
| Worker process limit (v0.2.5) | `max_processes` bounds DataEval's worker processes | None; the default is unchanged. |

## New data coverage workflow

Assess label-space, embedding-space, and metadata factor gaps before training.

### How to use

1. Configure the workflow. `ontology` takes an inline mapping or a path to an RDF artifact; without it, a flat
   ontology is synthesized from the dataset's `index2label`:

   ```yaml
   workflows:
     - name: coverage_check
       type: data-coverage
       ontology: config/taxonomy.ttl
   ```

2. Reading an ontology from an RDF file needs the extra:

   ```bash
   pip install "dataeval-flow[ontology]"
   ```

See {doc}`the coverage tutorial <../../notebooks/data_coverage>` and
{doc}`Declare an ontology <../../how_to/declare_an_ontology>`.

## Metadata encoding policies

Encodings are now nameable, exportable, and verifiable. An encoding is how continuous factors are cut into bins and
categorical factors are mapped to codes.

### How to use

1. Define a top-level `metadata:` policy in your configuration:

   ```yaml
   metadata:
     - name: standard
       encoding: policy/factor_bins.json
       continuous_factor_bins:
         elevation: 8

   workflows:
     - name: coverage_check
       type: data-coverage
       metadata: standard
   ```

2. Extract and pin the encoding from an existing run:

   ```bash
   dataeval-flow encoding output/results/result.json -o policy/factor_bins.json
   ```

3. Review the descriptor. Entries still reading `provenance: "derived"` are ones nobody has checked. Ratify them by
   setting `provenance` to `"accepted"` or `"declared"`.

See {doc}`Configure metadata binning <../../how_to/configure_metadata_binning>`.

## Explicit value range for float imagery

Float imagery has no inherent range. Without one, the visual statistics, pixel histogram and entropy, and
dimension depth answer `NaN`.

### How to use

Set `value_range` directly on any workflow that computes image statistics:

```yaml
workflows:
  - name: quality_check
    type: data-cleaning
    value_range: [-50.0, 50.0]
```

## Renames and removals

### Configuration keys

The old keys are deprecated but still function:

- `selections` → `views`
- `steps` → `operations`
- `selection` → `view`

```yaml
views:                          # was: selections
  - name: first_5k
    operations:                 # was: steps
      - type: Limit
        params: {size: 5000}
```

### Result fields

- Classwise outlier pivots: `level` is now `count_basis` (`image` or `annotation`).
- Per-factor metadata: `bins`, `bin_count`, `bins_requested`, `binned_by`, `categories`, `category_count`,
  `is_binned`, and `is_digitized` are replaced by `encoding` (the cut) and `fit` (what this run's rows did
  against it).

---

## Other enhancements and platform updates

- Result envelopes now include `metadata_binning`, `encoding_digest`, and `diagnostics`.
- Python 3.14 is fully supported.
- Dataset loaders moved from `maite-datasets` to `datamaite`.
- The view operations `Crop`, `Resize`, `SelectChannels`, and `TorchvisionTransform` are now supported. See
  {doc}`Narrow a dataset with views <../../how_to/build_dataset_views>`.

---

## Upgrade checklist

1. Clean the cache with `rm -rf <cache_dir>/v0`. See
   {doc}`Reuse results with the disk cache <../../how_to/reuse_results_with_cache>`.
2. Recompute the stored image statistics and the chance-corrected `Balance` rankings.
3. Add `value_range` for workflows on float imagery.
4. Rename `selections` / `steps` / `selection` → `views` / `operations` / `view`.
5. Run `dataeval-flow encoding` to pin and review your metadata encodings.
6. Adjust code that reads `level` or old bin/category fields from output JSONs.

## Patch releases

### v0.2.1

Released 2026-08-21. This patch renames the CUDA container variants to track the builds PyTorch publishes, restores
per-split loading for YOLO datasets, and corrects an example config that advertised fields the v0.2.0 schema had already
removed.

The published image tags now track the CUDA builds PyTorch publishes. `cu118` and `cu128` are no longer built, so a
`docker pull` naming either fails.

| Was | Now | Base |
| --- | --- | --- |
| `cu118` | `cu126` | Ubuntu 24.04 |
| `cu128` | `cu130` | Ubuntu 24.04 |

The `cpu` tag is unchanged. The `onnx-gpu` extra split the same way, into `onnx-cu126` and `onnx-cu130`, because an
`onnxruntime-gpu` wheel links against one specific CUDA major and has to match the PyTorch build:

```bash
uv sync --extra cu130 --extra onnx-cu130
```

```bash
docker pull harbor.jatic.net/aria/dataeval-flow:latest-cu130   # was: :cu128
```

The image name and tag in that command are the ones in force since v0.2.4, described below. Host requirements follow the
CUDA major: a 525-series or newer driver for `cu126`, 580-series or newer for `cu130`. The CUDA runtime libraries ship
inside the image, so no host CUDA install is needed. See
{doc}`Run workflows in containers <../../how_to/containerized_workflows>`.

Selecting one split of a YOLO dataset was lost when the loaders moved from `maite-datasets` to `datamaite`. It is
available again through a `split` field on the dataset config. Keep `path` on the dataset root so `data.yaml` stays in
scope. Pointing it at a split subdirectory falls back to numeric class names.

```yaml
datasets:
  - name: yolo_train
    format: yolo
    path: yolo-data          # dataset root: data.yaml + image/label trees
    split: train             # train | val | test; omit to load every split
```

Two optional fields cover non-standard layouts: `yaml_file` for a config that is not at the root under a conventional
name, and `ann_dir` for labels kept outside the `labels/` sibling of `images/`. Both are relative to `path`. An empty
load now names the split it was asked for, and points at the layout that split was expected to have.

:::{note}
`images_dir`, `labels_dir`, and `classes_file` on YOLO configs, and `classes_file` on COCO configs, were removed in
v0.2.0 and are rejected by the schema. The shipped example config advertised them by mistake until v0.2.1.
:::

The `opencv` extra is capped at `4.12.0.88` so installs succeed on FIPS-enabled systems.

To apply this patch:

1. Repoint container pulls by replacing the `cu118` / `cu128` image tags with `cu126` / `cu130`.
2. Replace the `onnx-gpu` extra with `onnx-cu126` or `onnx-cu130`, matching your CUDA variant.
3. Check that the driver is 525-series or newer for `cu126` and 580-series or newer for `cu130`.
4. Add `split:` to YOLO configs that need one split, and drop any `images_dir` / `labels_dir` / `classes_file` fields
   copied from an older example config.

### v0.2.2

Released 2026-08-24. This patch adds options to the headless CLI and a health summary to every result. It needs no
change to a config.

- `--task NAME` selects tasks by name. They run in the order you give, whatever their `enabled` setting says.
- `--fail-on-warning` makes the run exit non-zero when a health threshold is breached.
- `--version` reports the installed build.
- `dataeval-flow workflows` lists the workflow types and prints the JSON Schema of each one's parameters.
- Result envelopes carry a `health` block, with `status`, `warnings` and `findings`, beside `metadata`.
- `WorkflowResult` exposes the same information from Python as `health`, `warning_count` and `findings`. The
  `select_tasks` helper resolves the tasks that ran, so that you can pair them with results.

The patch also fixes a runner crash when results were paired with tasks marked `enabled: false`.

### v0.2.3

Released 2026-09-22. This patch lets the environment set the CLI parameters, timestamps the console log, and requires
DataEval 1.1.1 or newer.

- `DATAEVAL_*` environment variables configure the CLI parameters, and a CLI argument takes precedence. This release
  reads `DATAEVAL_CONFIG`, `DATAEVAL_DATA`, `DATAEVAL_OUTPUT`, `DATAEVAL_CACHE`, `DATAEVAL_LOG_FORMAT`,
  `DATAEVAL_FAIL_ON_WARNING`, `DATAEVAL_TASKS` and `DATAEVAL_VERBOSITY`. `DATAEVAL_TASKS` applies only to headless
  execution, not to the subcommands.
- `--no-fail-on-warning` turns off `DATAEVAL_FAIL_ON_WARNING` for a single run.
- `--log-format {structured,plain}` selects structured or plain log output. Console logs now include ISO-8601 UTC
  timestamps and levels. Pass `--log-format plain`, or set `DATAEVAL_LOG_FORMAT=plain`, to get bare messages as before.

The container image changed to match:

- The entrypoint honors `DATAEVAL_OUTPUT` and `DATAEVAL_CACHE` in place of hardcoded paths.
- The image creates `/cache/.not_mounted`, and an unmounted `/cache` is no longer exported as `DATAEVAL_CACHE`.

Object-detection datasets are now recognized consistently on Python 3.10 and 3.11, which prevents misclassification or
crashes. Two changes concern maintainers: `scripts/release.py` cuts and tags releases from the current branch, and the
GitHub release body carries the changelog section in place of `Release vX.Y.Z`.

If a tool reads the console log as bare messages, pass `--log-format plain` after you upgrade.

### v0.2.4

Released 2026-09-23. This patch moves the container images to a new repository, changes their tags and hardens how they
are built. Update every pull.

- The images publish to `harbor.jatic.net/aria/dataeval-flow` in place of `harbor.jatic.net/aria/dataeval`.
- `main-<variant>` tracks the default branch, and `latest-<variant>` is a retag of the newest stable release.
- The floating `<variant>` and `<major>.<minor>-<variant>` tags are removed. Pull `latest-<variant>`, or pin
  `<version>-<variant>`.
- All variants build on `ubuntu:24.04`, and the CUDA runtime and cuDNN install from Python wheels.
- Images are scanned before publication, and a HIGH or CRITICAL finding fails the build in place of being reported
  afterward.
- A published image carries its own vulnerability scan report and CycloneDX SBOM at `/usr/share/dataeval-flow/security/`.
- Prerelease tags (`vX.Y.Z-rcN`) publish as GitHub prereleases in place of replacing the latest stable release.

```bash
docker pull harbor.jatic.net/aria/dataeval-flow:latest-cpu   # was: harbor.jatic.net/aria/dataeval:cpu
```

To apply this patch:

1. Replace the repository in every image reference, in pulls and in deployment files.
2. Replace a floating `<variant>` or `<major>.<minor>-<variant>` tag with `latest-<variant>` or `<version>-<variant>`.

### v0.2.5

Released 2026-10-08. This patch adds a limit on DataEval's worker processes and requires DataEval 1.1.4 or newer.

- `max_processes` in the config bounds the worker processes. The `--max-processes N` CLI option and the
  `DATAEVAL_MAX_PROCESSES` environment variable set the same bound and override the config. Without any of them,
  DataEval runs in one process. Extra processes cost start-up time and pay off mainly on large images or heavy
  statistics.
- The run records the value in each result's `resolved_config`.
- The package requires `dataeval>=1.1.4`, and the lock files and container images resolve DataEval 1.1.4.
- Container images no longer ship the standalone interpreter's bundled `pip`, which nothing used.
- `nox -s verify` writes `output/metarepo/test-results.log`, a per-test-case log for metarepo assessments.

If you install into an environment that pins DataEval below 1.1.4, raise the pin before you upgrade.

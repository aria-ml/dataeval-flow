## Library

### v0.1.x alpha (shipped)

The initial alpha line establishes the workflow orchestration framework and the built-in evaluation workflows, published
to PyPI through v0.1.2. See [CHANGELOG.md](CHANGELOG.md) for the full list.

- [x] Workflow orchestration framework: registry, task runner, pipeline configuration
- [x] Data cleaning workflow (outlier + duplicate detection)
- [x] Data analysis workflow (statistical summaries); replaced by `audit`, which judges train and its evaluation
  splits before training and gives a verdict
- [x] Dataset splitting workflow (stratified and random strategies)
- [x] Drift detection workflow (classwise drift)
- [x] Out-of-distribution (OOD) detection workflow
- [x] Prioritization workflow (dataset sample ranking)
- [x] Parameter sweep workflow (grid comparison over data cleaning), v0.1.1; replaced by task matrices, which run
  any task across a grid of settings
- [x] Interactive TUI app + simple CLI config builder
- [x] Disk-backed and in-memory result caching
- [x] HuggingFace, MAITE, TorchVision, ImageFolder, COCO, YOLO dataset adapters
- [x] ONNX, PyTorch, BoVW, Flatten, and Uncertainty embedding extraction
- [x] Multi-variant Docker containers (cpu, cu118, cu128 at the time) with Cosign signing
- [x] PyPI publishing from `v*` tags via GitHub Actions trusted publisher
- [x] Dynamic versioning via `hatch-vcs` (v0.1.1)
- [x] Sphinx documentation with tutorial notebooks
- [x] GitLab CI/CD with SAST / dependency / secret scanning + SBOM
- [x] 90% test coverage enforcement, 100% type completeness on public API

### v0.3.0 readiness verdicts and composable chains (shipped 2026-11-12)

v0.3.0 asks whether a dataset is ready to train on. Every workflow type became a preset, a chain of steps that a
custom workflow can reuse. The `audit` preset gives a verdict that a training job can gate on. The release also brought
the DataEval v1.2 upgrade and the release tooling. See [CHANGELOG.md](CHANGELOG.md) and
[What's new in v0.3](docs/source/home/whats_new/v0.3.md). The release was targeted for October 2026 and waited for
DataEval v1.2.0, which was released on 2026-11-03. It requires DataEval v1.2.1, released on 2026-11-10, for the
Feasibility output that the `feasibility` evaluator reads.

- [x] Depend on a released `dataeval>=1.2.1` in place of DataEval `main`
- [x] Python 3.10 support dropped: the minimum is now Python 3.11, and the supported range is 3.11 to 3.14
- [x] Every workflow type is a preset that expands into a chain of evaluators, checks and transforms, and custom
      workflows chain those steps and presets directly
- [x] The `audit` preset gives a verdict over train and its evaluation splits, and `--require` gates on it
- [x] New `bias`, `taxonomy` and `triage` presets, and one `shift` preset in place of `drift-monitoring` and
      `ood-detection`
- [x] A task `matrix:` runs any task across a grid of settings, and replaces `parameter-sweep`
- [x] An HTML report with thumbnails of the items each finding names, and JUnit and Markdown summaries for CI
- [x] Content digests, per-item manifests and `dataeval-flow verify`
- [x] Plugin entry points for workflows, evaluators, transforms, extractors and image transforms
- [x] `ExperimentalWarning`, and the experimental `sufficiency`, `feasibility` and `parity` steps
- [x] A signed PEP 740 attestation for each file of a PyPI release
- [x] Poetry support dropped: `poetry.lock` and the `poetry install` lane removed; v0.2.5 is the
      last release to support it. uv, pip, and conda remain (supersedes SR-3-H-2..4)
- [x] `scripts/release.py` cuts a release from `main` or a `release/vX.Y` branch: it promotes the hand-written
      `## Unreleased` changelog section, commits and tags, and needs no GitLab API. It replaces the planned
      `release::*` label automation and its CI scripts
- [x] Release branch lifecycle (`release/vX.Y` long-lived branches): cut from a release tag,
      patched by cherry-pick from `main`; `latest-<variant>` moves only to the highest stable release,
      so a patch on an older line never moves it backwards. See BRANCHING.md (RS-5-S-1)
- [x] Container scan promoted to a gate: container scanning runs `allow_failure: false` at
      `CS_SEVERITY_THRESHOLD: HIGH`, blocking floating-tag promotion (CS-2-H-2 / DSOR-3-H-2)
- [x] SBOM published with releases: per-image CycloneDX cosign attestation (CS-2-H-4)
- [x] Link checking gates merges (DR-3.3-H-4). README's links to this project's docs are checked against
      the page sources, and a 502-504 or 429 response does not fail it
- [x] `dataeval-flow serve` (preview): a long-running HTTP service, in every image behind the `service` extra,
      that queues pipelines and runs each as the batch command. IR-2.3-H-2, IR-2.3-S-1 and IR-2.4-S-1
      now apply, and its health, liveness and readiness endpoints and OpenAPI description meet them

### v0.4.0 FMV and ontology workflows with on-disk format interop

Target: December 2026

Picks up new capabilities from upstream `dataeval` and a new sibling package, `databridge`, which handles on-disk
dataset format conversion so `dataeval-flow` can consume any supported source without bespoke loader code per format.

- [ ] Full Motion Video (FMV) workflow: wrap the FMV evaluation surface from `dataeval` (frame-level drift / OOD /
      quality) behind a `dataeval-flow` workflow type with the same config / orchestration / caching contract as the
      nine existing presets.
- [ ] Standalone ontology workflow: the `taxonomy` preset already consumes an ontology (inline hierarchy or RDF
      artifact) for label-space gap analysis (`scope` refuses one). This promotes the remaining `dataeval` taxonomy
      surface (class-mapping audits, cross-dataset label alignment) to a workflow of its own.
- [ ] `databridge` integration: depend on the new `databridge` package for on-disk format interop (HuggingFace ↔ COCO
      ↔ YOLO ↔ MAITE). Replaces the per-format adapter code currently in `src/dataeval_flow/_dataset.py` with a single
      `databridge`-backed loader.
- [ ] Container / CI plumbing: new optional `fmv` extra for the FMV decoder stack (likely `decord` / `pyav`), and
      document GPU requirements for video workflows.
- [ ] Tutorials + how-tos for FMV and Ontology workflows (cross-link from the existing tutorials and how-to guides per
      DR-2.4 / DR-2.5).

## Workflows

### Existing workflows, supported and maintained

The nine shipped workflows continue to receive bug fixes and minor enhancements throughout the v0.x line, and a task
matrix runs any of them across a grid of settings:

- Quality, Audit, Scope, Splits, Shift (drift and OOD detection, including classwise), Prioritization,
  Taxonomy, Bias, Triage

### Planned additions (TBD)

The following workflow ideas are under consideration for v0.4 / v1.0. Specifics to be refined by the team and reflected
here.

- [ ] Data validation workflow, TBD: define data-card output format and validation checks beyond what `quality`
      currently surfaces.
- [ ] Monitoring workflow, TBD: streaming / batch model + data drift monitoring with cached baselines (parallel to
      dataeval App Phase 2).

## Interoperability

### Currently supported

| Area | Supported |
| ---- | --------- |
| Datasets | HuggingFace Vision, COCO, YOLO, TorchVision, ImageFolder, raw MAITE objects |
| Models / extractors | ONNX, PyTorch, BoVW (SIFT), Flatten, Uncertainty |
| MAITE protocols | Consumes MAITE-compatible image classification and object detection datasets |
| MAITE entry-points | Declared in `pyproject.toml` for dataset protocols and `maite.tasks` (IR-1-H-3) |
| Exports | COCO, YOLO, Hugging Face and VisDrone, each with a `provenance.json` |
| Distribution | PyPI (`dataeval-flow`), Harbor container images (cpu / cu126 / cu130), ReadtheDocs |
| Service | `dataeval-flow serve` takes pipelines over a versioned HTTP API (`/v1`) |

### Planned or under consideration (TBD)

- [ ] Video dataset support, primary target dataset for the JATIC program; coverage to land via `databridge` in v0.4.0.
      IR-3.2-S-3 / IR-3.3-S-3 (VisDrone) will be exception-tracked in the meta-repo.
- [ ] TFLite model format (IR-3-S-2): decision pending; document as exception if descoped.
- [ ] Video workflows (IR-3.3-S-*): first concrete delivery is the FMV workflow in v0.4.0; full video-format coverage
      continues to track `dataeval` v2.0.
